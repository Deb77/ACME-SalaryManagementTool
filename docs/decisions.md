| 23 | 2026-11-20 | RBAC with roles in the database: `roles`, `permissions` and `role_permissions` tables, one role per user, each role a permission set plus a country scope (`all` or `assigned`). Escalation rules are in [auth.md](auth.md#roles-and-permissions-rbac). |
| 24 | 2026-11-20 | Country HR imports only their assigned countries. | 25 | 2026-11-20 | Invite links are copied by hand in v1 (shown once to the inviting user); no email | Send invites by email | Email needs a provider and domain setup, and with about 20 users copying a link is workable. |
| 26 | 2026-11-20 | Money is formatted in the currency's own locale (₹32,40,000 for INR), not the viewer's | Format in the viewer's browser locale | Matches how each country's HR team reads its own numbers, and the same amount looks the same for everyone. |
| 30 | 2026-11-20 | Drizzle ORM (`drizzle-orm` 0.45, `drizzle-kit` 0.31) for the schema, migrations and queries; supersedes the Kysely part of #7. The schema is TypeScript in `apps/api/src/db/schema`; `drizzle-kit generate` writes SQL migrations to `apps/api/drizzle`, and the app applies them itself (`npm run db:migrate`). Data, extensions, helper functions and the one `INCLUDE` index are hand-written SQL migrations. The 10,000-employee seed is a deterministic generator (`npm run db:seed`) | Keep Kysely; Prisma | An ORM with typed models and generated migrations, while staying close to SQL. Drizzle can express what database.md needs (checks, partial indexes, composite foreign keys, RLS policies) where Prisma's schema cannot, and RLS scoping is a plain `set_config` in a transaction. |
| 31 | 2026-11-20 | Inversion of control in the API with a small typed container (`apps/api/src/lib/container.ts`, about 60 lines) and one composition root (`apps/api/src/container.ts`). Services and repositories are classes that take their collaborators in the constructor; routes are factories that receive the services they call | awilix, tsyringe or InversifyJS; module-level singletons imported directly | Constructor injection keeps every dependency visible and lets tests swap one entry (a fixed clock, a quiet logger) without mocking modules. A typed registry gives compile-time checks without decorators or `reflect-metadata`; the container is small enough to read in one sitting. |
| 32 | 2026-11-20 | The API connects with `DATABASE_URL` and runs every connection as `acme_app` (`-c role=acme_app` at connect). Migration `0005` creates `acme_app` as `NOLOGIN NOBYPASSRLS`, grants it to the migrator, and adds the grants and RLS policies. Policies are not `FORCE`d | A separate `acme_app` login with its own password (auth.md); `SET ROLE` per transaction | Same protection (the API never runs as the table owner, so RLS always applies and DDL is impossible) without a second password to manage on Render's single-user plan. A deployment can still `ALTER ROLE acme_app LOGIN PASSWORD …` and point `DATABASE_URL` at it. Without `FORCE`, the owner (migrations, seed) bypasses RLS, so the seed needs no scope. |
| 33 | 2026-11-20 | RLS details beyond auth.md: `salary_changes` is filtered by its own copied `country_code` (no join); audit events are visible when in scope, when you are the actor, or (for all-country roles) when they have no country (user and role admin); imports are visible to their uploader or when every touched country is in scope, and only the uploader can change one. Generated employee codes and import undo's deletes run in two small `SECURITY DEFINER` functions | Policies exactly as sketched in auth.md | The copied country (decision #27) keeps the salary policy an index condition. Admin audit rows have no country, so without the extra clause Global HR could not see "who invited whom". Code generation must see every country's codes, which RLS would hide. |
| 34 | 2026-11-20 | Sign-in and invite screens in the web app (`/sign-in`, `/accept-invite#token=…`); the invite token travels in the URL fragment. New contracts: `signInRequestSchema`, `acceptInviteRequestSchema`, `inviteInfoSchema` and query schemas for audit, insights and import rows | Token in the query string | A fragment is never sent to the server, so the token cannot leak through access logs or the Referer header. |
| 35 | 2026-11-20 | Changes from the end-to-end review (browser at six viewports, every endpoint timed and checked against the Zod schemas, `EXPLAIN` as `acme_app`): sign-in limits count only failures, per IP and email (10) plus per IP (50); hire and termination dates cannot be in the future, and leavers are read-only; salaries are capped at 1,000,000,000 major units (`MAX_SALARY_MINOR`) so payroll sums stay exact; unknown filter values return 400; the list counts in a separate query; new indexes `employees_name` and `audit_events_actor_occurred`; no trigram index | Keep a per-IP limit on every attempt; a window `count(*) over ()`; the E2 trigram index | A per-IP limit on all attempts locked a whole office out after ten sign-ins. Future-dated hires and leavers broke the "current salary and status are plain columns" rule. The window count made every page sort all rows in scope (11 ms → 0.5 ms for the first page). ILIKE is not leakproof, so a trigram index cannot be used under RLS, and search measured 3.5 ms without one. |
| 36 | 2026-11-21 | Ask AI answers with generated SQL through one `run_sql` tool, run as the separate login `acme_ai_reader` (migration `0007_ask_ai`). Each statement goes through a real Postgres parser (`libpg-query` 18.2.4): exactly one `SELECT`, no `INTO` or locking, allowed tables and functions only, no `reg*` casts. It then runs wrapped with a 200-row cap (and 20,000 characters of JSON) in `begin read only` … `rollback`, with a 5 s timeout. The scope comes from `app_private.ai_scope`, which `acme_app` writes from the session and keys by the reader's backend PID | Typed tools over the repositories (the earlier api.md design); `SET ROLE` from `acme_app`; regex checks on the SQL | HR questions vary too much for a few fixed functions. The protections are in the database (no `BYPASSRLS`, read-only, timeout, no `TEMP` or `CREATE`, column grants, RLS) and in a parser rather than in the model's behaviour. A separate login means `RESET ROLE` cannot climb back, and `set_config()` from model SQL changes nothing. |
| 37 | 2026-11-21 | No names or emails reach the model. Column grants leave out `first_name`, `last_name`, `email`, `termination_note` and `salary_changes.note`. `find_employee_codes(name)` returns at most 10 codes (with title, country and status). The web app shows "Name (code)" by looking codes up through the employees API | Views without the columns (database.md open question 5); letting the model read names | Grants make a leak a permission error, not a prompt rule. Views would need `security_invoker` and a second set of policies. Resolving codes in the browser uses the user's own RLS scope. |
| 38 | 2026-11-21 | Ask AI budgets: 150k tokens per conversation, 1M per user per day (both counted from stored messages), 6 tool rounds and 2,000 output tokens per answer, 20 messages a minute and 200 a day (`429` with `Retry-After`). Going over a token budget is `429 ai_budget_exceeded` ("Start a new conversation" or "Try again tomorrow"). The system prompt and tools are prompt-cached. All are `AI_*` env settings | Only a message rate limit; a monthly spend cap in the Anthropic console only | Keeps one conversation and one person from running up cost, while the per-user context (today, countries) sits after the cache breakpoint so caching still hits. |
| 39 | 2026-11-21 | AI drafts store `version_at_draft` and `expires_at` (7 days) and apply once: a second apply is `409 draft_applied` (unique index S3), and a draft whose employee changed or that is older than 7 days is `409 draft_stale` ("This draft is out of date — ask again"). The audit row carries `aiDraftId`. `draft_salary_change` is offered only to users with `salary:change` | Drafts that never expire; re-checking only the amount | An old suggestion should not be applied over a newer change without a fresh look, and the audit log shows which changes started as AI suggestions. |
| 40 | 2026-11-21 | Models: primary `claude-sonnet-5-5`, fallback `claude-opus-5-5` (`AI_MODEL_PRIMARY`, `AI_MODEL_FALLBACK`), 30 s per call and no SDK retries. A call that errors, times out or refuses before any text has streamed is retried once on the fallback. Without `ANTHROPIC_API_KEY` or `DATABASE_URL_AI` Ask AI returns `503 ai_unavailable` and the rest of the app starts normally | The API's server-side `fallbacks` beta; retrying after text has streamed | An app-level fallback is visible in our metrics and logs and works the same with any model. Switching after text has streamed would repeat or contradict the answer. |
| 41 | 2026-11-21 | SQL audit log `ai_sql_runs`: one row per `run_sql` attempt (ok, rejected, error, timeout) with SQL text, countries, status, error, row count, duration and model, never result rows. It is written in its own transaction and is append-only (`SELECT, INSERT` for `acme_app`, nothing for the reader). Read through `GET /api/ai/sql-runs` (`audit:read`; own runs, or all runs for all-country roles), keyset-paged | Logging the SQL only; storing results | Lets anyone check what the assistant actually ran, including what the guard stopped, without keeping copies of salary data. |
| 42 | 2026-11-21 | Ask AI monitoring without new dependencies: JSON log lines per turn (`ai.turn`) and per SQL run (`ai.sql_run`) with OpenTelemetry-style field names, never containing questions, answers, results, names, emails, SQL text (length only) or the key. In-process counters and latency histograms at `GET /api/ai/metrics` (`users:manage`) and, when `METRICS_TOKEN` is set, Prometheus text at `/metrics` behind a bearer token. `GET /api/health` reports AI status. Alerts (error rate, fallback rate, daily tokens; `AI_ALERT_*`) are logged once per window as `ai.alert` | The OpenTelemetry SDK; a hosted APM | Enough to see cost, failures and fallbacks on one Render instance. The field names map onto OTel if we add a collector later. Metrics reset on restart, which is acceptable at this size. |
| 43 | 2026-11-21 | Ask AI evals in `apps/api/src/evals`: 27 cases against the seed generated with `seed: 42, asOf: 2026-11-01`, with expected answers computed in code from `generateSeedData`. They include adversarial cases (prompt injection, names and emails, writes, multi-statement, scope escape, private notes). A code grader checks numbers within a tolerance, required text, leaks in answers and logs, and the audit rows (no successful read of a denied column, every run in the user's scope, nothing forbidden succeeded, data unchanged). `npm run evals` uses the real model; the CI suite uses a scripted model that must pass every case, and a careless one that must fail every case | An LLM judge; hand-written expected numbers | Computed answers stay right when the generator changes. A code grader is free, repeatable and cannot be talked round. An LLM judge can be added later as a separate, optional step for free-text quality. |
| 44 | 2026-11-21 | Ask AI shows its steps in plain English (the model's `purpose` and the row count), never the SQL. Neither the stream nor the conversation endpoint sends SQL or tool arguments to the browser; reviewers read the SQL in the audit log (`GET /api/ai/sql-runs`, `audit:read`) | Showing the SQL under each answer (the first build); hiding it with CSS only | HR users don't read SQL, and it exposed table and column names to everyone with `ai:ask`. Hiding it only in the UI would still leave it in the network responses. The audit log keeps it checkable for the people whose job that is. |

## Open questions

Raised by the design docs and not decided yet:

- Can Render's default Postgres user create the `acme_app` role (migration 0005)? If not, create it once from Render's shell as an admin and re-run the migration.
- Where the demo password lives (README or submission note only).
- Future-dated salary changes, moving an employee to another country, and reinstating a terminated employee (all rejected in v1).
- Import: a time limit on undo.
